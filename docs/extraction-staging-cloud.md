## Activation sequence

1. **Prepare an independent staging target.** Use a [schema-only root branch](https://neon.com/docs/guides/branching-schema-only) or a separate empty project to avoid copying production user/session/chat records. Inspect any existing candidate before reusing it; do not reset or replace another environment. The fully isolated web deployment needs an application/auth database and a distinct extraction-review database on staging. The app's `DATABASE_URL` and `EXTRACTION_STAGING_DATABASE_URL` must differ; neither should target the live database. Pin the actual production host/database using the password-free `EXTRACTION_STAGING_LIVE_DATABASE_IDENTITY` URL. Cloud mode rejects either staging connection if it matches that live identity, including direct/pooled aliases. Recheck project/branch/endpoint IDs through Neon metadata before applying SQL, since URL comparison alone cannot prove arbitrary aliases are independent. Free-plan root/compute/storage allowances are shared within each project and must be checked first.
2. **Prepare private evidence storage on that same staging root.** Choose a new private bucket or verify the existing bucket's access level. Create a `storage:read` runtime credential on staging, and a separate credential with both `storage:read` and `storage:write` for the offline uploader. Real-provider testing found that a write-only credential could not perform the ACL/policy checks required before uploading; declaring both scopes resolved this. Do not create them on production: [Neon credential lineage](https://neon.com/docs/storage/authentication) permits descendant branches. Keep operator keys out of Vercel. Do not use automatic environment pulls that overwrite `.env` or the main database configuration.
3. **Initialize metadata separately.** Use the staging operator database connection and the existing `init --confirm-isolated ENVIRONMENT_ID` command. Create/use a restricted runtime database role with only the permissions described in the [review runbook](extraction-staging-review.md). Use a separately restricted auth role for the empty staging auth database. The web process must not receive operator/database-owner credentials or inherit a role that can grant review access.
4. **Configure the operator process.** Set the Neon branch ID, endpoint, region, bucket and scoped credentials from `.env.example`. The adapter requires HTTPS to the pinned branch/region host and uses a fixed environment/digest namespace. It rejects public ACLs, foreign canonical grantees and unreviewed allow policies. A provider response that cannot establish privacy is a hold; do not bypass it merely to make the smoke test pass.
5. **Upload the validated evidence.** The following is an explicit write action, not part of `plan`. It requires a distinct upload credential and exact environment confirmation. It verifies the whole local bundle and byte budget first, reuses existing matching objects, refuses corrupt replacements, sends deterministic content-addressed keys, then downloads and rehashes new objects. No object deletion or metadata approval occurs. Interrupted uploads leave only unregistered objects; retries reverify them and resume. Only after every required object is present should the existing `import` command register the immutable candidates against the cloud adapter.

```sh
npm run extraction:staging -- upload --bundle work/pdf-staging/import-v2 --confirm-environment allabouttax-extraction-dev
npm run extraction:staging -- import --bundle work/pdf-staging/import-v2
```

6. **Prepare preview hosting.** Select a stable Vercel preview URL, explicitly scope environment settings to the staging branch/project and set `AUTH_URL` to that URL. Register that exact Google OAuth callback through the account owner before testing real sign-in; do not reuse an incorrect production callback. Only the read-only storage credential and restricted database credentials belong on the web deployment. The review feature stays off in production. A local evidence backend is rejected when enabled on Vercel because its disk is ephemeral.
7. **Grant and test real access.** Have the owner sign into staging, identify that staging user ID, and use the operator grant command with reason/expiry. This does not copy their production admin role or grant tax-review authority. Verify an ordinary signed-in user gets denied, the selected reviewer can view originals and save a draft, the draft survives deployment/reload, a stale edit conflicts, revocation denies both API and image/PDF access, and the table remains blocked. Smoke-test the actual provider's ACL/policy responses and read-only credential scope; mocks cannot establish those properties.
8. **Back up and restore before broader use.** Back up immutable candidate/revision/head records together with the content-addressed evidence inventory. Restore into another isolated test namespace and compare all hashes and revision chains, then retest denial and blocked scopes. Keep production activation and tax/RAG release as later explicit steps.

## Operational limits

The AWS S3 SDK is pinned and configured for [Neon's path-style API](https://neon.com/docs/storage/s3-compatibility). The runtime exposes no upload/delete/presigned-URL endpoint. Complete evidence reads enforce a 15-second object deadline, 45-second candidate deadline, literal byte limits, declared length and SHA-256. Each operator transfer has a three-minute network deadline and resumes on retry. Range/partial responses, missing or altered objects fail closed. Reader cancellation does not wait indefinitely for a broken transport. Existing session/capability checks still protect downloads, with no browser/CDN caching of the app response.

The runtime hashes source dependencies on review reads and writes, so repeated inspection downloads evidence repeatedly. Measure latency and network usage on the pilot before increasing volume. Files are never declared immutable merely because the key contains a hash. Neon currently stores versioning/lifecycle configuration without enforcing it; the adapter is **not WORM storage** and does not claim timed retention/deletion. Conditional upload headers and content-addressed writes do not replace separate backups or a verified object-lock policy. The upload credential remains a trusted operator capability; it includes deletion powers even though this tool never issues deletes.

`tests/extraction-storage.test.ts` verifies private-bucket checks, endpoint pinning, real SDK signing/serialization with a local transport, source integrity and delivery budgets, cancellation, interrupted upload recovery and non-overwrite behavior. It uses no real cloud credentials. A completed preview build alone does not confirm cloud storage, OAuth, real reviewer access or production readiness.
